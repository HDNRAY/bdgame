# 战斗统计设计（伤害统计 · 出招诊断 · log 收口）

> 内部设计文档。目标是把「战斗里发生了什么」「为什么没发生」这两件事收成一套统计，
> 同时服务三种用途：玩家看的战后小结、构筑/批量模拟的平衡分析、以及调参时的决策诊断。
> 玩家向表述另见 `docs/gameplay-guide.md`（本文件写实现口径，不写进玩法手册）。

---

## 一、目标与边界

**要解决的三种用途**

1. **战后展示**：一场打完，玩家能看到伤害构成、承伤、命中、治疗、资源、距离、触发与条件。
2. **平衡分析**：批量模拟（构筑试炼 / `npm run tour`）不只出胜率，还能出「每个角色的伤害构成、条件拦截率、平均交战距离」。
3. **决策诊断**：回答「这招为什么没出」「这条条件为什么没生效」。

**边界（不做的事）**

- 统计**只读**，不参与判定、不影响战斗结果、不进存档（战斗结束时按需取快照）。
- 引擎内**不做字符串格式化**，`format()` 只在展示层调用。
- 不为了统计在热路径分配对象：`level === 0` 时只多一次判断。

## 二、现状与三个问题

| 问题               | 现状                                                                                                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **统计长错了地方** | `StatsTracker` 挂在 log 监听器上，而 `emitLog` 在 `quiet` 模式第一行就 `return` → 批量模拟 / tour / 构筑试炼**完全收不到统计**，只有 `scripts/demo-battle.ts` 能打印 |
| **口径不全**       | 治疗只记名义量（无「有效 / 溢出」）；伤害有 `blocked` 但没细分「招架减免 / 减伤 / 护盾吸收 / 穿透」；召唤物伤害没标归属；「为什么没出招」没有任何数据来源            |
| **口径分散**       | DevMode `ActionCompare` 自己解析 log 算招式指标（含击退收益折算），与 `StatsTracker` 各算一套                                                                        |

## 三、架构：一条事件流，两个数据面，三级开关

```
                ┌── 结果面：引擎管道事件（damage / heal / attack_start / move / status_* …）
引擎事件流 ─────┤        → BattleStats（引擎持有，quiet 也能开）
                └── 决策面：规划期埋点（planEvent / generatePlans / pickActions）
                         → PlanDiagnostics（可空，null 时零成本）

log（叙事投影）   ←── formatBattleLog / ReplayEngine / LogPanel
stats（数值投影） ←── BattleStatsPanel / demo 脚本 / DevMode 聚合
```

**关键决定：统计从 log 里搬出来。** log 继续只负责叙事文本与回放；统计由引擎持有的 `BattleStats`
在管道里更新。这样 `quiet` 路径也能开统计，批量模拟才有整体视角。

**log 与 stats 共用同一个发射点**：事件字段补齐后，log 是事件流的叙事投影、stats 是数值投影，
不存在两套口径。

**决策面独立**：`PlanDiagnostics` 由规划函数选择性接收，`null` 时热路径零成本。

### 三级开关（`StatsLevel`）

| 级别     | 内容                                       | 默认开启处                        |
| -------- | ------------------------------------------ | --------------------------------- |
| `0` 关   | 什么都不收                                 | 大量模拟时的最快档                |
| `1` 基础 | 输出、承伤、命中、治疗                     | 批量模拟 / tour（够平衡分析用）   |
| `2` 完整 | 再加资源、距离、状态、触发与条件、决策诊断 | UI 战斗（单场 / 肉鸽 / 构筑试炼） |

## 四、事件字段（第一步已落地的部分）

统计要算得准，事件先要带够信息。

| 事件                       | 补什么                                                                                    | 状态                                                                                                                                                                                                                                                                                             |
| -------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `heal`                     | `effective`（实际回血）、`overheal`（溢出）                                               | **已做**：`applyHeal` 与 `heal_over_time` 两处都按 hp 前后差记账                                                                                                                                                                                                                                 |
| `attack_start` / `support` | `chanCost`（缠劲消耗）                                                                    | **已做**：触发招式不耗内息但要耗缠劲，之前没有任何事件带这个数                                                                                                                                                                                                                                   |
| `damage`                   | 附伤不另加字段：引擎已经在 `tags` 里标了 `bonus_damage`                                   | **已做**（用 tag 判定）                                                                                                                                                                                                                                                                          |
| `damage`                   | `piercing` / `absorbed` / `mitigated` / `parriedAmount` 细分，`isSummon` / `ownerId` 归属 | **待做**：要动伤害管道（`applyDefenseStages` / `onAbsorb`）与召唤物发射点，风险高于收益，等 UI 真的需要再补。当前口径：`final` = 实际扣血，`blocked` = 减免总量（不细分）                                                                                                                        |
| 资源                       | 不加事件：改由 `Character` 自己记账                                                       | **已做**：新资源事件要在热路径上多发日志，而资源流动的**唯一必经之路**就是 `Character` 的四个方法（`spendAp` / `gainAp` / `addChan` / `spendChan`）。在这四个方法里累加 `Character.res`（`ResourceTally`），战斗结束时 `BattleEngine.syncResourceStats()` 一次性同步给 `BattleStats`，零事件开销 |
| `move`                     | 已有 `delta / newDistance / durationMs / kind`                                            | 够用                                                                                                                                                                                                                                                                                             |
| `attack_start`             | 已有 `triggered` / `summonName`                                                           | 够用                                                                                                                                                                                                                                                                                             |

**决策面**（新增，仅 level 2）：`planEvent` 产出一份诊断，记录

- 每个候选招式的淘汰原因：`gate`（条件不满足）/ `ap` / `chan` / `distance` / `cap`（本回合名额已满）/ `rate`（效率比输给某招）；
- 每条条件的拦截次数；
- 每个触发槽的触发次数与收益。

## 四·五、已实现（第一步交付物）

- **顺带确认了「统计不能长在 log 上」**：`BattleLog` 在重建事件时会丢字段——log 里的 `attack_start` **不带 `actionId`**（只有 `actionName`），所以按招式统计命中/招架/闪避这条路在 log 上根本走不通（旧的 `stats-tracker` 是残缺的）。引擎管道里的原始事件才带全字段。
- **`src/engine/combat/battle-stats.ts`**：`BattleStats` + `StatsLevel`（0/1/2）。字段分两层：`CharStat`（角色）+ `ActionStat`（角色 × 招式）；
  另有 `merge()`（脚本跑 N 场聚合）、`snapshot()`（Map 换数组，供 UI）、`format()`（文本报告）。
- **接入点**：`BattleEngine.enableStats(level)` + `emitLog()` **最前面**调用 `stats.handle(event)`——在 `quiet` 短路之前，所以批量模拟也能收集；
  `runBattle(..., { statsLevel })` 是脚本/UI 的入口（第 6 个可选参数，向后兼容）。
- **删除** `stats-tracker.ts`（挂在 log 监听器上的旧统计）。
- **命中面板的权威来源**（这一步最关键的修正）：
  | 数字 | 来源 |
  | --- | --- |
  | 出手 | `attack_start` |
  | 判定次数 | 命中 + 被闪避（= `check_hit` 的次数，连发一招多判） |
  | 命中 / 被闪避 | `check_hit.result`（true / false） |
  | 被招架 | `check_parry.result` |
  | 暴击 | `check_crit.result` |
  | 打中但零伤 | `命中 − 造成伤害的事件数`（被吸收/减免到 0 时不会发 `damage`） |
  | 失手 | `fumble`（发生在 `attack_start` 之前，所以不计入出手数） |
  顺带发现两处事件问题：**`parried` 日志事件没有任何生产者**（招架只走 `check_parry`），`dodged` 事件与 `check_hit` 重复——统计一律只认 `check_*`，不看这两个事件。
- **对账规则**（报告里必须成立）：`判定 = 命中 + 被闪避`；`命中 = 造成伤害 + 打中未造成伤害`。
- **「出手」与「判定」是两个数**（这一步才看清）：`attack_start` 一次出手可能带多段命中判定（连发 / 多段招式，原子回合 `totalHitsMax = 1 + 连发数`），
  所以 `判定 ≥ 出手`，用出手当命中率分母会算出 > 100% 的命中率（唐柔实测 143%）。
  正确定义：**命中率 / 被闪避率的分母是判定次数**，**暴击率 / 被招架率的分母是命中**（招架只在命中之后判定）。
  由此还能直接读出「平均每招几段」= 判定 / 出手。
- **资源统计补全**（第二步之前顺手做掉，它属于「数字对不对」而不是「界面长什么样」）：
    - 口径从「事件字段猜」换成「角色自己记账」。原来的 `缠劲消耗` 只数了 `attack_start.chanCost`，
      于是**武器 / 奇物 / buff 自扣的缠劲全丢**——典型例子是李雪影的「电磁战术刀」（`onAfterDealDamage` 里
      `attacker.spendChan(1)` 追加电伤），报告里她的缠劲消耗是 0；移动消耗的内息也从来没数过。
    - `ResourceTally` 七个字段：`apSpent` / `apDrained` / `apGained` / `apWasted` / `chanGained` / `chanSpent` / `chanOverflow`。
      被扣（打断、破气）与主动消耗分开，因为玩家会问「我的内息是被花掉的还是被扣掉的」。
    - 顺带统一了内息写入入口：新增 `Character.gainAp(amount)`（返回实际增量，负值表示净回复被压低，如御物耗炁），
      原先散在引擎与效果处理器里的 `char.ap = Math.min(...)` 赋值全部改走它。
    - **对账不变式**（已写成测试）：`初始 AP（起手 50%）+ apGained − apSpent − apDrained = 终值 AP`，
      `chanGained − chanSpent = 终值缠劲`。
    - **踩到的坑**：AI 期望伤害的沙盘（`ai/expected-damage.ts`）用 `Object.create(char)` 做原型克隆，
      赋值类字段（`chan` / `ap` / `hp`）写入落在克隆自身，所以以前没事；但 `res` 是**对象**，
      钩子里的 `spendChan` 会原地改它 —— 推演时每次「假装花缠劲」都累加进真实角色的统计，
      实测把唐柔的缠劲消耗从 26 抬到 50（虚高近一倍）。修法是 `Character.forkForSim()`：
      沙盒克隆必须自带一份 `res`。这条同样适用于以后任何「挂在角色上的可变对象」。
- **实测开销**（3000 场 quiet 对战，各跑两轮）：level 0 = 6.77/6.80 ms/场，level 1 = 6.80/6.86，level 2 = 6.86/6.88 —— 即 **+0.5% ~ +1.3%**。折算到 tour（49,600 场 / 约 100 秒），level 1 约多 1 秒。
    - 资源记账（`Character.res`）即便 level 0 也在跑：同脚本同机器 A/B（5 组满配对手，1500 场 ×2 轮）差异在噪声内（level 0 = 10.41/10.48 vs 10.45/10.84；level 2 = 10.24/10.22 vs 10.35/10.39 ms/场），不值得为它加开关。
    - 补全后重跑 tour：49,600 场 106.7 秒，胜率 46.3% ~ 52.7%（与补全前分布一致，资源数字不参与判定）。
- **验收**：`npm run demo`（`scripts/demo-battle.ts`）单场打印完整报告，`npm run demo 20` 走 `merge()` 聚合，均正常。

## 五、口径定义（先定死，避免「数字对不上」）

- **伤害**：以 `final` 为准（实际扣血，含穿透）；`base` 是减免前，`blocked` 是总减免量，
  减免构成 = 招架减免 + 减伤 + 护盾吸收。三者关系在 UI 上必须标清。
- **DoT 单列**，不混进直接伤害；**附伤**（`bonus`，雷法 / 金光那类）单列或归入来源招式，二者选一后全站统一。
- **召唤物**：伤害归主人（用 `isSummon` / `ownerId` 上卷），同时在明细里可展开看召唤物本体。
- **治疗**：有效治疗 = 实际回血；溢出 = 名义量 − 有效。UI 默认显示有效，溢出作为次要信息。
- **资源**：角色级数字只有一个来源 —— `Character.res`（角色自己记账，战斗结束同步）。事件字段只用于「按招式归属」，
  两者**不允许互相补差**：总账多出来的部分恰恰是「不属于任何招式的消耗」（移动、被打断、武器与 buff 自扣）。
  展示时外面是消耗，括号里是流水明细（回复 / 浪费 / 被扣、获得 / 溢出），避免玩家把「回复」误读成「消耗」。
- **时间/回合**：分段统一用 `log scope[0]`（回放的分段也用它），保证统计与回放对得齐。
- **「一次出手」**：以 `attack_start` 为准（无论中不中）；命中 / 闪避 / 被招架 / 暴击都以它为分母。

## 六、分区（每个分区回答一个玩家会问的问题）

| 分区     | 数据面      | 回答                                                                                                                                                                                               |
| -------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 输出     | 结果        | 每招总伤与占比；直接 / DoT / 附伤拆分；每点内息换多少伤害                                                                                                                                          |
| 承伤     | 结果        | 被谁打、挨了多少；减免构成（招架 / 减伤 / 护盾）占比                                                                                                                                               |
| 命中面板 | 结果        | 每招出手数、命中率、闪避率、被招架率、暴击率                                                                                                                                                       |
| 治疗     | 结果        | 有效治疗、溢出、治疗来源                                                                                                                                                                           |
| 资源     | 结果        | 内息消耗 / 回复 / 浪费 / 被扣；缠劲消耗 / 获得 / 溢出。角色总账来自 `Character.res`（覆盖招式、移动、武器与 buff 自扣、被打断、时间回复）；`ActionStat.apSpent/chanSpent` 只做「按招式归属」的明细 |
| 距离     | 结果        | 平均交战距离、贴脸 / 风筝时间占比、位移招用量                                                                                                                                                      |
| 状态     | 结果        | 我给对手挂上什么、成功率；我身上减益的覆盖时长                                                                                                                                                     |
| 触发     | 结果 + 决策 | 触发招式用了几次、贡献多少；哪些槽一次都没触发                                                                                                                                                     |
| 条件     | 决策        | 每条条件拦了几次；哪条条件从未命中（等于写了不生效）                                                                                                                                               |
| 决策诊断 | 决策        | 每招淘汰原因分布（门槛 / 内息 / 缠劲 / 够不着 / 名额 / 效率比输给谁）                                                                                                                              |

- **A/B 对照**：在原有胜率对比表之外加一张指标对照表（输出 / 出手 / 命中率 / 暴击率 / 被闪避率 / 被招架率 / 承伤 / 内息 / 缠劲 / 交战距离 / 贴脸占比 / 挂状态成功率），

  只统计 A、B 都跑到的对手，保证可比。
- **`SeriesResult.stats`**：worker 回传的每个对手结果里带一份 `BattleStatsSnapshot`（`runSeries` 内每场 `merge` 到 `BattleStats.accumulator`）。
  快照必须是纯数据 —— 有测试守着它可 `structuredClone`（否则 worker 传不回来）。
- **顺带修掉的口径错**：这一层把「命中率」暴露给了玩家，才看清 `出手` 与 `判定` 不是一个数（见第四节）。

## 九、性能验收

- `level 0`：热路径只多一次 `level === 0` 判断。
- `level 1`：每次相关事件几次累加 + Map 查找，不做字符串、不分配数组。
